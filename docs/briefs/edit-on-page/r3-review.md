# Release 3 review (22 Nov 2026)

An adversarial review of `phase-2-r3` at 584a0f3: four finders (data safety, accessibility, visual fidelity, security), an Opus skeptic per dimension who tried to refute each finding, and a Fable check of the design vision. Only confirmed findings are listed; refuted ones are left out. The fix round assigns each item to agent X (data), Y (layout and vision) or Z (accessibility and small items).

### data-safety-1. [high] A picture uploaded but not yet placed can be deleted from storage by an autosave, then silently stripped from the saved exhbt
- Where: `components/exhbt-editor/files.ts:95`
- Scenario: The person picks 5 pictures (two uploads run at once). Picture 2 finishes before picture 1, so it is in `seen` (line 164) and in `results` but is not placed, because `place()` only places the settled run from the front (line 140). While picture 1 is still uploading, an autosave lands (for example the person typed alt text on an already placed picture, or a save was in flight). `noteSaved` calls `settle()`. Picture 2's file is not in the server doc, the live copy, `store.get()` or any undo entry, so `settle` DELETEs it. `/api/files/[id]` finds no exhbt using it and removes the record and the object. When picture 1 lands, `place()` inserts picture 2 with the dead fileId. The picture shows during the visit from its object URL. The next save runs `ownDocOnly`, which drops any image section whose file is not owned, so the picture vanishes from the stored doc. On reload it is gone with no message. The same hole exists in two shorter windows: `replaceImage` (files.ts:211-215) calls `seen.add` and then `await readSize(file)` before `store.patch`, and `FigureSheet.take` (FigureSheet.tsx:70-71) calls `files.addUploaded` and then `await readSize(file)` before `patchDoc`. A save landing in either await deletes the new file before it is on the page. The comment on `addUploaded` says an unplaced upload is deleted at the next run of the rule, but nothing stops that run happening before the placement.
- Evidence: files.ts: `settle()` keeps only fileIdsOf(serverDoc), live, fileIdsOf(store.get()) and undoable files. `addImages` does `seen.add(fileId)` on upload success but places only through `place()`, which waits on `settled[placedUpTo]`. lib/exhbt/doc-files.ts `withoutFiles` drops image sections whose file is not owned, and lib/store.ts `saveExhbtDraft` calls `ownDocOnly`.
- Proposed fix: Keep a `pending` set of fileIds that are uploaded but not yet placed or abandoned. Add the id when the upload returns (addImages, replaceImage, addUploaded) and remove it when the placement is made or given up. Have `settle` skip anything in `pending`. In FigureSheet's `finally`, release the id explicitly before calling `files.settle()`. Alternatively, call `seen.add` only at the moment the section is inserted into the store.
- Skeptic (confirmed): I could not refute this. The person does not even need to type for it to happen. In addImages (files.ts:153-174), each finished upload goes into `seen` straight away (line 164), but place() (140-152) only places the run of settled uploads from the front. Placing picture 0 changes the doc, so useAutosave saves about 1.5s later (useAutosave.ts:144). onSavedDoc then calls files.noteSaved, which runs settle() (files.ts:260-263). settle keeps only the server doc, the live copy, the current doc and the undo entries' files (95-104). It also tops up `seen` from the current doc, so an upload that has finished but is not placed stays in `seen` and is DELETEd. Take a batch of the shape fast, slow, fast: picture 0 is placed, picture 1 is still uploading (a big GIF is never shrunk, media.ts prepareImage), and pictures 2 and 3 are finished. Both 2 and 3 get deleted. The DELETE route (app/api/files/[id]/route.ts) only checks the stored docs, which do not hold them, so lib/uploads.ts deleteFile removes the object and the exhbt_files row. When picture 1 lands, place() inserts 2 and 3 with dead fileIds. They still show from their object URLs. The next saveDraft goes through saveExhbtDraft and ownDocOnly (lib/store.ts:1117-1118 and 689-691), and withoutFiles drops image sections whose file no longer exists. They are gone on reload, and publishExhbt publishes the stored blocks without them. No test covers files.ts. replaceImage (211-215) and FigureSheet.take (FigureSheet.tsx:70-71) have the same hole, but only for the length of one createImageBitmap call (readSize). So those two are real but minor; the addImages path is what makes this high.

### data-safety-2. [low] Any non-network server error on save is treated as a stale editor: no retries, and the status tells the person to reload
- Where: `components/exhbt-editor/Autosave.tsx:23`
- Scenario: The person is typing. `saveDraft` fails for a transient reason: a Supabase timeout (`check()` throws inside the action), a Cloudflare 5xx, or an expired session or feature flag (`notFound()`). The client promise rejects with a plain `Error` ("An error occurred in the Server Components render" or "An unexpected response was received from the server"), not a `TypeError`. `isNetwork` is false, so `send` logs it as a stale editor and returns `{ ok: false, error: STALE_EDITOR }`. `useAutosave` treats `ok: false` as a final server refusal (`attempt = TRIES`), so the 3 tries with backoff never happen. The top bar then shows "The editor was updated. Reload to carry on" with a Reload button instead of Retry. The classic editor retried this case three times and said "Couldn't reach the server". The next edit does retry, so this is not silent data loss, but the guarantee that a blip does not stop saving is gone and the message is false. A person who reloads relies on the backup offer.
- Evidence: Autosave.tsx lines 23-35: only `TypeError` or `navigator.onLine === false` count as network. Everything else is mapped to STALE_EDITOR. components/editor/useAutosave.ts lines 80-92: `r.ok === false` stops the retry loop.
- Proposed fix: Classify as stale only the specific signs of a missing server action (for example a message containing "Failed to find Server Action" or a 404 from the action endpoint). Treat any other thrown error as retryable by rethrowing it, so useAutosave's three tries run. Optionally treat it as stale only after the retries fail.
- Skeptic (confirmed): The code does what the finding says. send() (Autosave.tsx:27-36) turns anything that is not a TypeError, or a throw while the browser is online, into { ok:false, error: STALE_EDITOR }. useAutosave then treats ok:false as final and sets attempt = TRIES (useAutosave.ts:97-101), so the three tries never run. SaveStatus then shows the "editor was updated, Reload" words. Two transient failures reach this branch. One is check() throwing inside saveExhbtDraft (lib/store.ts:675-678): the action promise rejects with a plain Error. The other is a non-RSC 5xx response: Next 15.5's server-action-reducer.js:104-107 throws a plain Error (E394), 'An unexpected response was received from the server.'. Decision 0026 line 277 does choose no retry for non-network failures, so that part is a recorded design choice. The defect is the test being too broad. Next throws a separate UnrecognizedActionError for a truly missing action (reducer line 66), so the two cases can be told apart. I did not rely on the expired-session sub-case: signedIn() calls redirect(), not notFound(), and how the client handles that depends on runtime behaviour. I graded it down from medium. No work is lost: the browser copy stays because clearBackup runs only on success, the next edit saves again, an unmount flushes, and beforeunload warns. The trigger, a server failure, is off the common path. The false 'Reload' instruction is the visible harm.

### data-safety-3. [medium] "Restore them" can overwrite newer work with an older browser copy, cannot be undone, and "Discard them" can delete the live backup
- Where: `components/exhbt-editor/EditorShell.tsx:350`
- Scenario: The person opens the editor. A backup newer than the server copy exists, so the offer banner shows. They ignore it and fix the title and a finding. Autosave saves the new text, and `writeBackup` has already replaced the stored copy with it. The banner stays on screen, still holding the old `offer` object in memory. Later they press "Restore them". `store.replace(normaliseDoc(offer.doc))` puts the old doc over everything typed since, clears the undo list, and autosave saves the old doc to the server. Nothing says which text was lost and there is no Undo. If they press "Discard them" instead, `clearBackup(env.id)` removes the stored copy, which by now holds their current unsaved edits. A crash before the next change then has no browser copy.
- Evidence: EditorShell.tsx BackupOffer: `offer` is read once in the useState initialiser and never reset when the doc changes. `onClick` calls `store.replace(...)` and `clearBackup(env.id)` unconditionally. store-core.ts `replace` sets `stack = []`. The store's `onChange` calls `writeBackup` on every change under the same key.
- Proposed fix: Drop the offer, or turn it into a one-way choice, as soon as the person makes a first change (store.version() > 0). Alternatively, make Restore an undoable `patchDoc` entry, and make Discard clear the backup only while the stored copy is still the offered one (compare `at`).
- Skeptic (confirmed): The Restore half is confirmed. BackupOffer (EditorShell.tsx:350-356) reads the backup once in its useState initialiser. Nothing hides it when the doc changes, and it is position: fixed over the page (css/core.css:566). If the person edits first and presses 'Restore them' later, store.replace(normaliseDoc(offer.doc)) runs (line 367). store-core.ts replace() (337-342) sets stack = [], so there is no Undo, and autosave then saves the old doc over the newer work. One more effect: pictures uploaded this visit are no longer in the doc or in any undo entry, so the next settle() deletes their stored files as well. The Discard half is weak. useAutosave clears the backup on every clean save anyway (useAutosave.ts:115), so the exposure is only the ~1.5s before an edit is saved, plus a crash in that window. The classic editor has the same offer logic (components/editor/Editor.tsx:447-468), so this was carried over rather than new in release 3. It is still real in the editor that is now the default.

### data-safety-4. [low] Text typed in the "Add a skill" box is lost if the person does not press Enter or comma

### data-safety-5. [low] Undo of a flowchart add or move silently does nothing after an AI rewrite of the flowchart that changed the number of boxes
- Where: `components/exhbt-editor/undo.ts:196`
- Scenario: The flowchart has 5 boxes and the person adds box 5 (entry E1 holds key K4). They run "Rewrite" on the process, which returns 3 boxes. `syncKeys` keeps K0 to K2 and drops K3 and K4. They press Undo, which reverts the rewrite and restores 5 boxes. `applyUndo` returns the old `keys` array of length 3 and `commit` pads it with fresh keys, so K4 is gone. They press Undo again for E1. `keys.indexOf(K4)` is -1, so `f.op === "add" && at >= 0` is false. The entry is popped, the live region says "Undone", and the added box is still there. The same loss of keys defeats the undo of an older box move or remove.
- Evidence: undo.ts lines 190-205: a flow op is applied only when its key is found in `keys`. store-core.ts `syncKeys` (positional re-keying) runs after a rewrite or undo that changes `doc.flow.length`, and `applyUndo` does not restore the keys of a `keys` entry for the flow array.
- Proposed fix: When an entry changes `doc.flow` (a rewrite or a restore through `patchDoc`), record the keys before and after it, and put them back on undo. Or apply a flow op by position when its key is missing.
- Skeptic (confirmed): Confirmed by this deterministic path, which needs no AI call. The AI drafted 4 boxes. The person adds box 5: flowAdd pushes { flow: {op:'add', key:K4} } (store-core.ts:237-245). They press 'Back to the AI version' of the process: patchDoc with replaceBlock, draft-tools.tsx:56, which sets doc.flow back to 4 boxes. commit then runs syncKeys (133-136), which cuts the keys to [K0..K3]. Undo restores the 5 boxes through the entry's `keys`, but applyUndo returns the cut keys unchanged and commit pads them with a fresh key, so K4 is gone. A second Undo does keys.indexOf(K4) === -1, so the add branch (undo.ts:200-203) is skipped. The entry is still popped and UndoKeys says 'Undone: add box 5' while the box stays. An AI rewrite that changes the box count goes the same way. Two corrections to the finding. Undo of a remove is not defeated: that branch runs exactly when the key is absent (undo.ts:204-207) and puts the step back at f.at. Undo of a move fails only when the moved box's key sat past the point where the keys were cut. Nothing is lost: the box can still be removed by hand.

### accessibility-1. [low] A failed save is never announced to screen readers
- Where: `components/exhbt-editor/topbar/SaveStatus.tsx:26`
- Scenario: A screen reader user keeps typing, and the save fails (offline, or the editor is stale after a deploy). SaveStatus changes from the 'saved' branch to the error branch. The root span is reused (same element type) but loses role=status. A new <span role=status> is inserted already holding 'Kept in this browser.' (or the stale-editor words). Live regions that arrive with their text already in them are not reliably announced. The only visible change is a 'Not saved. Retry' button in the top bar, which is out of the user's focus. The user believes their work is saved and carries on, and later closes the tab. The same applies to the Reload message in the stale case (lines 14-18).
- Evidence: SaveStatus.tsx: the saved/saving branch has role=status at line 38, the error branch inserts a fresh role=status span at line 31, and the stale branch does so at line 16. There is no persistent live region and no ui.say on a save error. grep of components/exhbt-editor finds the only other live regions in EditorShell's LiveRegion and the sheets, and none of them is fed by the save state.
- Proposed fix: Keep one always-mounted role=status container, and put the changing text inside it. Also call ui.say('Not saved. ...') (or use role=alert for the error text) when the state turns to error.
- Skeptic (confirmed): The structure is as described. In the saved and saving states the root is `<span role="status" className="xe-save">` (SaveStatus.tsx:38). In the error branch (25-35) React reuses that span, drops role=status and inserts a new `<span role="status">` (line 31) that already holds 'Kept in this browser. …'. A live region inserted with its words already in it is not reliably announced, so I would say 'not reliably announced', not 'never'. The work is not at risk. useAutosave keeps a copy in localStorage on every change (useAutosave.ts:141), and beforeunload asks before leaving whenever the state is not 'saved' (165-173), so 'later closes the tab' brings up the browser's leave prompt. The path is uncommon (offline, or a deploy since the page opened), so low, not medium. The fix stands: keep one always-mounted status element and change only its text, or say the error through ui.say or role=alert.

### accessibility-2. [medium] Focus is lost to the page top when the figures sheet or chart sheet opened from the + menu is closed
- Where: `components/exhbt-editor/Insert.tsx:86`
- Scenario: A keyboard user opens the '+' menu and chooses 'Take a figure from my report', or chooses a graph block. choose() calls setOpen(null), which unmounts the menu item that has the focus, and then runs the action. The action either opens a sheet (uiApi.open('figure')) or flushSync-adds a graph and then opens the chart sheet (engine.afterAdd). When Sheet.tsx's effect records its opener, document.activeElement is already <body>. When the sheet is closed with Escape or Cancel, there is nothing to return to (body.focus() does nothing), so focus stays on <body>. The user must Tab from the top of the document through the whole top bar again to get back to where they were. WCAG 2.4.3.
- Evidence: Insert.tsx:86-89 choose() runs setOpen(null) before run(). Sheet.tsx:22-26 reads opener from document.activeElement at open time. - Skeptic (confirmed): Confirmed for both paths. Insert.tsx:69-72 `choose` calls setOpen(null) and then run(), in the same click handler. Figure path (line 131): uiApi.open('figure') updates an atom read through useSyncExternalStore (atom.ts:33-38), so both updates land in the same commit. The menu, and with it the focused item, is removed in the mutation phase. Sheet.tsx's effect (20-27) then runs and reads document.activeElement, which is <body>, so opener = body. Graph path (line 116): board.add then addAt then withMotion's flushSync (engine.ts:621-626), which commits the queued setOpen(null) as well; afterAdd (engine.ts:629-630) then calls ui.open('chart') with nothing focused in between. On Escape, Cancel or ChartSheet's Done (ChartSheet.tsx:59), onClose calls back.focus() on body (Sheet.tsx:40-45), which does nothing. The native dialog's own focus restore also goes to body. This breaks 0026's own rule ('focus goes back to what opened them'). The e2e test e2e/editor-drag.spec.ts:876-881 presses Escape after the graph sheet opens but never checks where the focus went. FigureSheet's success path does move focus to the new picture's description (FigureSheet.tsx:86-93), so only closing without taking a figure loses it. Where the next Tab lands after that depends on the browser, but the focus is not returned to the '+' or to the new section.

### accessibility-6. [low] Every section's toolbar is role=toolbar but takes four to six Tab stops with no roving focus or arrow-key movement
- Where: `components/exhbt-editor/Toolbar.tsx:78`
- Scenario: On a page of 8 sections a keyboard user passes five or six tab stops (grip, up, down, action, more, remove) at the top of every section before reaching its words, so about 45 Tab presses to reach the end of the page.
